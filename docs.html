1. Platform Overview

Cyphr is a studio toolset with two distinct products sharing a common backend. Everything is built as self-contained single-file HTML applications — no build step, no framework, no npm. The backend is a Python Flask API deployed on Railway.

ProductWhat it doesPrimary user
Cyphr FlowAI-assisted proposal builder — brief → estimate → proposal → SOW → downloadCyphr studio team
Blarney IntelligenceAnalyse Samsung kiosk AI conversations — flags, journeys, benchmarksClient (Samsung/Blarney project)
Intelligence DashboardGeneral-purpose brief and project analysisCyphr studio team
QA Dashboard / ReviewTest case management and QA review workflowsQA team

High-level architecture

Browser (GitHub Pages / local)
  │
  ├── Cyphr Flow (index.html)
  │     ├── POST /gemini  ──────────→  Cloudflare Worker  ──→  Gemini 2.5-flash
  │     ├── POST /generate ─────────→  Railway API (app.py)  ──→  Claude Haiku
  │     └── File ops  ──────────────→  Railway API (app.py)
  │
  └── Blarney Intelligence (blarney-intelligence.html)
        ├── POST /ai-flag ──────────→  Railway API (app.py)  ──→  Gemini 2.0-flash
        ├── POST /benchmarks ───────→  Railway API (app.py)  ──→  Brave Search + Gemini
        └── GET/POST /snapshot ─────→  Railway API (app.py)  ──→  GitHub Gist
No database. All project data lives in the browser's localStorage. The Railway API is stateless — every request contains all the data it needs. The only persistent server-side storage is GitHub Gist, used exclusively for Blarney session snapshots.

2. Applications

Cyphr Flow — index.html

The main studio tool. A project is created once and moves through a fixed pipeline of stages. Each stage builds on the previous one — the brief feeds the estimate, the estimate feeds the proposal, and so on. All data is stored in localStorage under the key cyphr_projects.

Response caching (added July 2026)

Before every Gemini call, a hash of all input fields for that stage is computed. If the hash matches a cached result in localStorage, the stored result is returned instantly — no API call, no cost. The cache is invalidated automatically when any input field changes. Shift+click any generate button to force a fresh call.

Blarney Intelligence — blarney-intelligence.html

Analyses conversation transcripts from Samsung kiosk AI sessions. A CSV of sessions is uploaded, parsed locally, and pushed to Railway for persistence. AI-powered safety flagging runs against the transcripts via the Railway /ai-flag endpoint.

Dashboard tabs

  • Flags & Alerts — rule-based and AI-detected safety issues. Categories: jailbreak, offensive, hallucination, offbrand, frustration. Severity: high / medium / low.
  • Advertising — decision-moment quotes, top customer questions, voice of customer, competitor mentions.
  • Journeys — customer journey cards grouped by conversion outcome.
  • Internal — drop-off analysis, talk ratio, unanswered questions, frustration signals.
  • Your Wins — live benchmark comparisons from Brave Search + Gemini analysis.

Automatic flagging rules (pattern-based, no API cost)

Session data format (CSV columns)

Session ID, Date, Mode, Transcript, Buy In Store, Buy Online (QRs), ...

Transcript format: lines prefixed [User] or [AI]. Mode is typically "Kiosk" or "QR".

3. Backend API (Railway)

A Flask REST API. Deployed on Railway as a Docker container using Gunicorn. Handles document generation, AI flagging, benchmark fetching, and session snapshot storage. All API keys are stored as Railway environment variables — nothing in the code.

Container:  Python 3.11-slim
Server:     Gunicorn, port 8080, 120s timeout
URL:        https://cyphr-api-production.up.railway.app

All routes

POST /generate POST

Generates a Word, PowerPoint, or Excel document from project data. Returns the binary file for download.

Request body:
{
  "type": "brief" | "sow" | "proposal" | "proposal-pptx" | "estimate" | "gantt" | "status",
  "projectData": {
    "clientName": string,
    "projectName": string,
    "sector": string,
    "budget": string | number,
    "timeline": string,
    "requirements": string,
    "bgNotes": string,
    "briefOutput": string,   // pre-generated AI text
    "estimateOutput": string,
    "proposalOutput": string,
    "sowOutput": string
  }
}

Returns: Binary .docx / .xlsx / .pptx file
Filename: {client-slug}_{type}.{ext}
AI used: Claude Haiku (default) for generation; no AI call for brief/SOW (renders pre-generated text)

POST /ai-flag POST

Runs Gemini 2.0-flash over batches of kiosk transcripts, returns detected safety flags.

Request body:
{ "transcripts": [ { "Session ID": string, "Date": string, "Mode": string, "Transcript": string } ] }

Returns:
[
  {
    "sessionId": string,
    "date": string,
    "category": "jailbreak" | "offensive" | "hallucination" | "offbrand" | "frustration",
    "severity": "high" | "medium" | "low",
    "message": string,   // exact customer message
    "reason": string     // one sentence explanation
  }
]

AI model: gemini-2.0-flash (hardcoded)
Output cap: 2,048 tokens
Key source: GEMINI_KEY env var

POST /benchmarks POST

Fetches live industry benchmarks via Brave Search, then runs Gemini analysis to compare against the submitted metrics. Falls back to static benchmarks if the live pipeline fails.

Request body:
{ "metrics": { "conversionRate": number, "engagementRate": number, "avgTurns": number, "competitorRetention": number } }

Returns: Array of benchmark win objects (where our metrics beat the industry figure)

Live pipeline: Brave Search → parse snippets → Gemini extraction → comparison
Fallback: STATIC_BENCHMARKS (Forrester, Gartner, Salesforce, McKinsey figures)

POST /push-snapshot POST

Stores Blarney session records to a GitHub Gist for shared access across browsers.

Request body: { "rows": array }
Returns: { "ok": true, "raw_url": string }
Storage: GitHub Gist (GIST_ID env var), file: blarney-snapshot.json

GET /snapshot GET

Returns the stored Blarney session snapshot from GitHub Gist.

Returns: JSON array of session records

POST /push-intel-snapshot POST

Stores intelligence/analysis data to a separate GitHub Gist.

Request body: any JSON object · Storage: INTEL_GIST_ID Gist, file: intelligence-snapshot.json

GET /intel-snapshot GET

Returns: Stored intelligence JSON object, or null

GET /health GET

Returns: { "status": "ok", "provider": string, "api_key_set": boolean }

Output validation

Every generated document is passed through a verify_output() check before returning:

  • Template bleed — checks for previous project names (Blue Square, Samsung, MentorLink, lorem ipsum) that shouldn't appear
  • Invented names — flags two-word capitalised names not in the team config or source notes
  • Budget overrun — warns if any calculated fee exceeds the user's stated budget by more than 20%
  • Placeholder convention — missing or unconfirmed data surfaces as [CONFIRM: reason] so incomplete documents are obvious before sending

8. Hosting — Current Setup & Next Steps

How it is set up now — GitHub

All frontend HTML files live in a GitHub repository (cyphr-flow). GitHub Pages serves them publicly as static files directly from the main branch — no build step, no server. Every git push to main automatically updates the live site within seconds.

FileLive URL (GitHub Pages)
index.htmlhttps://[org].github.io/cyphr-flow/
blarney-intelligence.htmlhttps://[org].github.io/cyphr-flow/blarney-intelligence.html
intelligence.htmlhttps://[org].github.io/cyphr-flow/intelligence.html
docs.htmlhttps://[org].github.io/cyphr-flow/docs.html

The GitHub repository also stores all source history, acts as the deployment trigger (push = deploy), and hosts the Gist files used for Blarney snapshot storage via the GitHub API.

GitHub Pages limitations: No custom domain HTTPS without a CNAME file, no preview deployments per branch, no deployment logs, no rollback UI, and no environment variable support. Fine for the current stage — but as the platform grows, Vercel removes all of these friction points.

Next steps — Moving to Vercel & switching the domain

The plan is to move the static frontend from GitHub Pages to Vercel and point the cyphr.studio domain (or a subdomain) at it. The Railway backend, Cloudflare Worker, and GitHub Gist storage all stay exactly where they are — only the static host changes.

Why Vercel

  • Custom domain with automatic HTTPS — point flow.cyphr.studio at it, certificate is provisioned instantly
  • Preview deployments — every branch gets its own URL, so you can test changes before merging to main
  • Deployment logs and rollback — one click to go back to any previous version
  • Better CDN performance — global edge, HTTP/2, faster load times internationally
  • Zero config — Vercel reads the repo and deploys automatically, same as GitHub Pages but with more control

What moves and what stays

ComponentCurrent homeAfter migration
index.html, blarney-intelligence.html, all HTML filesGitHub PagesVercel (static)
Railway API (app.py)RailwayRailway — unchanged
Cloudflare Worker (Gemini proxy)CloudflareCloudflare — unchanged
GitHub Gist (Blarney snapshots)GitHubGitHub — unchanged
GitHub repo (source + git history)GitHubGitHub — unchanged. Vercel reads from it.

Migration steps

1
Create a Vercel account at vercel.com using your GitHub login — this lets Vercel access the repo without any token setup.
2
Import the repository — Vercel dashboard → Add New → Project → find cyphr-flow → Import. Vercel detects it as a static site automatically.
3
Set build config — Framework Preset: Other · Build Command: blank · Output Directory: ./ · Root Directory: ./. Click Deploy. You get a cyphr-flow.vercel.app URL in ~10 seconds.
4
Add the custom domain — Project Settings → Domains → add flow.cyphr.studio (or app.cyphr.studio). Vercel gives you a CNAME record to add in your DNS registrar. HTTPS certificate is automatic.
5
Update Google OAuth origins — in Google Cloud Console → APIs & Services → Credentials → your OAuth client → Authorised JavaScript origins, add the new Vercel URL and custom domain. Without this, Google login will fail on the new domain.
6
Disable GitHub Pages — once Vercel is confirmed working on the custom domain, go to the GitHub repo → Settings → Pages → change source to "None". This avoids duplicate live sites.
7
Test the full flow — open the Vercel URL, log in with Google, create a project, generate a brief, download a document. Check network tab to confirm calls reach the Cloudflare Worker and Railway without errors.
After migration, deployments stay automatic. Every push to main on GitHub triggers a Vercel redeploy — same workflow as now, just with a proper domain and preview URLs for branches.
No code changes needed for the migration. All backend URLs in the HTML files (RAILWAY_URL, proxyUrl) are hardcoded to the Railway and Cloudflare services which don't change. The only things that need updating are the Google OAuth origins list and DNS records.
